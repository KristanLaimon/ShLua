# Luash Architecture

## 1. Purpose and boundaries

Luash is a dependency-free Lua 5.1-compatible transpiler. It accepts a documented Lua subset and emits Bash 3.2+
or PowerShell 3.0+ source. It is a source-to-source compiler, not a Lua interpreter: unsupported syntax is rejected
instead of being evaluated by the host Lua runtime.

The same compiler is exposed through two entry paths:

```
CLI:  main.lua -> Luash.main(args) -> read/compile/write
API:  require("luash") -> Luash.parse / Luash.transpile / Luash.compile
```

## 2. Compilation pipeline

```
Lua source
    |
    v
Lexer (src/lexer.lua)
    |
    v
Token stream
    |
    v
Parser (src/parser.lua)
    |
    v
Lua subset AST
    |
    v
Lexical scope resolver (src/scope_resolver.lua)
    |
    v
Standard-library analyzer (src/stdlib_analyzer.lua)
    |
    +--------------------------+
    |                          |
    v                          v
Bash translator          PowerShell translator
    |                          |
    v                          v
BashScript wrapper       PS1Script wrapper
    |                          |
    v                          v
Bash serializer          PowerShell serializer
    |                          |
    v                          v
.sh source               .ps1 source
```

`src/luash.lua` is the composition root. It registers targets, validates their interface contracts, runs the shared
front end once, and invokes targets in deterministic `bash`, then `ps1`, order when `all` is selected. `main.lua` is
only a location-independent launcher that adds `src/` to `package.path` and delegates to `Luash.main`.

## 3. Module responsibilities

| Module | Responsibility |
| --- | --- |
| `main.lua` | Thin executable launcher and exit-code propagation. |
| `src/luash.lua` | Public API, target registry, composition root, AST dump, and CLI orchestration. |
| `src/cli.lua` | Option parsing plus input/output file operations. |
| `src/lexer.lua` | Converts source text into tokens with source locations. |
| `src/parser.lua` | Produces the supported Lua AST using recursive descent and precedence climbing. |
| `src/scope_resolver.lua` | Resolves lexical bindings, block-local generated names, captures, and recursive names. |
| `src/stdlib_analyzer.lua` | Finds referenced base, math, string, IO, OS, and table libraries throughout the AST. |
| `src/ITranspiler.lua` | Validates the structural target-backend contract. |
| `src/bash_transpiler.lua` | Validates Bash constraints and serializes executable Bash 3.2+ source. |
| `src/ps1_transpiler.lua` | Validates PowerShell constraints and serializes PowerShell 3.0+ source. |
| `src/stdlib/bash/*.lua` | Maps supported Lua library calls to self-contained Bash helpers. |
| `src/stdlib/powershell/*.lua` | Maps supported Lua library calls to self-contained PowerShell/.NET helpers. |
| `run_build.lua` | Syntax-checks source modules and generates the single-file distribution. |
| `run_tests.lua` | Runs every maintained test file in an isolated Lua process. |
| `run_check.lua` | Runs build, syntax, format, lint, and distribution smoke checks. |

## 4. Public API

`require("luash")` returns a table with these stable alpha entry points:

- `Luash.VERSION`: current release identifier.
- `Luash.parse(source)`: returns the Lua subset AST.
- `Luash.transpile(source, target)`: returns one target string, or `{ bash, ps1 }` for `all`.
- `Luash.compile`: alias of `Luash.transpile`.
- `Luash.main(args)`: runs the CLI workflow and returns an integer exit code.

The CLI layer never selects or imports concrete backends. Target registration and ordering remain in `src/luash.lua`.

## 5. Transpiler contract and target wrappers

Every registered backend must provide:

- `name` and `extension` strings.
- `new()` returning a translator instance.
- `instance:translate(luaAST)` returning a target wrapper.
- `Serializer.serialize(targetAST)` returning executable source text.

The current wrappers are `BashScript` and `PS1Script`. They retain the resolved program, closure/function metadata,
the validated coroutine worker set, and the ordered standard-library modules required by the program. Target-specific
generator objects own quoting, expression mapping, statement rendering, runtime helpers, and final serialization.
Backend validation happens before output is emitted.

## 6. Standard-library injection

The shared analyzer walks all expressions and statements, including nested function bodies, and records library calls
and dotted constants. Each backend filters its strategy modules against that result. Serializers embed only the selected
helper source before user declarations, so generated scripts never load compiler files or shell modules at runtime.
The backend metadata pass also selects runtime fragments independently: Bash arithmetic, callable/closure dispatch, and
coroutine support are emitted only when generated code invokes them; PowerShell callable dispatch is likewise omitted
unless a closure or comparator needs it.

Library modules expose a small data contract: `name`, supported `functions`, optional `constants`, explicit
`unsupported` reasons, and embeddable `source`. Unsupported multi-return, pattern-iterator, and file-handle APIs fail
during transpilation rather than being emitted with different semantics.

## 7. Lua AST contract

The parser currently produces:

- Statements: `FunctionDecl`, `IfStmt`, `WhileStmt`, `RepeatStmt`, `NumericForStmt`, `GenericForStmt`, `DoStmt`,
  `BreakStmt`, `LocalVarDecl`, `AssignmentStmt`, `TableAssignmentStmt`, `MultiLocalVarDecl`, `MultiAssignmentStmt`,
  `ReturnStmt`, and `ExprStmt`.
- Expressions: `FunctionExpr`, `CallExpr`, `BinaryExpr`, `UnaryExpr`, `TableConstructor`, `IndexExpr`, `Identifier`,
  and `Literal`.
- `IfStmt` may include `elseifs` and `elseBody`.
- A dotted supported call such as `coroutine.resume(co)` is represented by a string callee on `CallExpr`.

Multiple assignment is intentionally accepted only for the two values returned by `coroutine.resume` in alpha.

The scope resolver annotates declarations, identifiers, and call targets with resolved names. It also records the
outer lexical bindings read by function expressions and captured named functions. This shared pass keeps both targets
on the same binding model even though their native shell scope rules differ.

## 8. Table lowering

Table variables carry references rather than copied collections. Keys are stored with type tags so numeric and string
keys with the same spelling remain distinct; sequence constructor fields receive independent 1-based keys. PowerShell
uses a hashtable wrapper containing ordinal .NET dictionaries. Bash 3.2 has no associative arrays and command
substitution loses process-local mutation, so Bash uses opaque handles backed by a private temporary directory and
cleans that directory on script exit. This also lets aliases and tables returned from functions retain mutable identity.

`pairs` snapshots the current encoded-key list and `ipairs` advances from numeric key 1 until the first missing entry.
The injected table strategy implements `concat`, `insert`, `maxn`, `remove`, and in-place `sort`.

## 9. Coroutine lowering

Alpha coroutines are compiled generators rather than suspended Lua stacks:

1. Each backend discovers top-level `coroutine.create(namedWorker)` calls.
2. It validates that workers are named, parameterless, and contain only sequential yields plus an optional final return.
3. Every created handle receives independent worker and state data.
4. Each resume advances a generated state machine and assigns `success, value`.
5. A resume after completion returns `false, "cannot resume dead coroutine"`.

Bash stores handle state in generated variables and dispatches through `__luash_coroutine_*` helpers. PowerShell uses
a hashtable handle and generated worker functions. Names beginning with `__luash_` are reserved for generated runtime
internals.

## 10. Single-file distribution

`run_build.lua` wraps every compiler module in `package.preload`, embeds them in `dist/luash.lua`, and appends a small
dispatcher. Loading that file through `require("luash")` returns the API; executing it runs the CLI. The generated file
uses only the Lua standard library and must not read modules from the repository at runtime.

## 11. Verification architecture

Compiler tests remain directly under `tests/`. Numbered dependency-free Lua script cases live under `tests/scripts/`
as `NN_<testName>.test.lua`, progressing from minimal programs to combined complex programs. Each script case writes
its generated Bash and PowerShell files beside the test, executes installed target shells, and leaves cleanup to
`run_tests.lua`, which removes only those generated `.sh` and `.ps1` artifacts after the complete suite.

Tests cover lexer/parser behavior, both serializers, progressively complex source programs, coroutine validation and
state transitions, real Bash and PowerShell execution when available, and isolated use of the bundled module and CLI.
The release gate is:

```
lua run_build.lua
lua run_tests.lua
lua run_check.lua
```
