# Luash Architecture

## 1. Purpose and boundaries

Luash is a dependency-free Lua 5.1-compatible transpiler. It accepts a documented Lua subset and emits Bash 3.2+
or PowerShell 3.0+ source. It is a source-to-source compiler, not a Lua interpreter: unsupported syntax is rejected
instead of being evaluated by the host Lua runtime.

The same compiler is exposed through two entry paths:

```
CLI:  main.lua -> Luash.main(args) -> read/compile/write
API:  require("luash") -> Luash.parse / Luash.transpile / Luash.compile
```

## 2. Compilation pipeline

```
Lua source
    |
    v
Lexer (src/lexer.lua)
    |
    v
Token stream
    |
    v
Parser (src/parser.lua)
    |
    v
Lua subset AST
    |
    +--------------------------+
    |                          |
    v                          v
Bash translator          PowerShell translator
    |                          |
    v                          v
BashScript wrapper       PS1Script wrapper
    |                          |
    v                          v
Bash serializer          PowerShell serializer
    |                          |
    v                          v
.sh source               .ps1 source
```

`src/luash.lua` is the composition root. It registers targets, validates their interface contracts, runs the shared
front end once, and invokes targets in deterministic `bash`, then `ps1`, order when `all` is selected. `main.lua` is
only a location-independent launcher that adds `src/` to `package.path` and delegates to `Luash.main`.

## 3. Module responsibilities

| Module | Responsibility |
| --- | --- |
| `main.lua` | Thin executable launcher and exit-code propagation. |
| `src/luash.lua` | Public API, target registry, composition root, AST dump, and CLI orchestration. |
| `src/cli.lua` | Option parsing plus input/output file operations. |
| `src/lexer.lua` | Converts source text into tokens with source locations. |
| `src/parser.lua` | Produces the supported Lua AST using recursive descent and precedence climbing. |
| `src/ITranspiler.lua` | Validates the structural target-backend contract. |
| `src/bash_transpiler.lua` | Validates Bash constraints and serializes executable Bash 3.2+ source. |
| `src/ps1_transpiler.lua` | Validates PowerShell constraints and serializes PowerShell 3.0+ source. |
| `run_build.lua` | Syntax-checks source modules and generates the single-file distribution. |
| `run_tests.lua` | Runs every maintained test file in an isolated Lua process. |
| `run_check.lua` | Runs build, syntax, format, lint, and distribution smoke checks. |

## 4. Public API

`require("luash")` returns a table with these stable alpha entry points:

- `Luash.VERSION`: current release identifier.
- `Luash.parse(source)`: returns the Lua subset AST.
- `Luash.transpile(source, target)`: returns one target string, or `{ bash, ps1 }` for `all`.
- `Luash.compile`: alias of `Luash.transpile`.
- `Luash.main(args)`: runs the CLI workflow and returns an integer exit code.

The CLI layer never selects or imports concrete backends. Target registration and ordering remain in `src/luash.lua`.

## 5. Transpiler contract and target wrappers

Every registered backend must provide:

- `name` and `extension` strings.
- `new()` returning a translator instance.
- `instance:translate(luaAST)` returning a target wrapper.
- `Serializer.serialize(targetAST)` returning executable source text.

The current wrappers are `BashScript` and `PS1Script`. They retain the parsed program and the validated coroutine
worker set. Target-specific generator objects own quoting, expression mapping, statement rendering, runtime helpers,
and final serialization. Backend validation happens before output is emitted.

## 6. Lua AST contract

The parser currently produces:

- Statements: `FunctionDecl`, `IfStmt`, `LocalVarDecl`, `AssignmentStmt`, `MultiLocalVarDecl`,
  `MultiAssignmentStmt`, `ReturnStmt`, and `ExprStmt`.
- Expressions: `CallExpr`, `BinaryExpr`, `UnaryExpr`, `Identifier`, and `Literal`.
- `IfStmt` may include `elseifs` and `elseBody`.
- A dotted supported call such as `coroutine.resume(co)` is represented by a string callee on `CallExpr`.

Multiple assignment is intentionally accepted only for the two values returned by `coroutine.resume` in alpha.

## 7. Coroutine lowering

Alpha coroutines are compiled generators rather than suspended Lua stacks:

1. Each backend discovers top-level `coroutine.create(namedWorker)` calls.
2. It validates that workers are named, parameterless, and contain only sequential yields plus an optional final return.
3. Every created handle receives independent worker and state data.
4. Each resume advances a generated state machine and assigns `success, value`.
5. A resume after completion returns `false, "cannot resume dead coroutine"`.

Bash stores handle state in generated variables and dispatches through `__luash_coroutine_*` helpers. PowerShell uses
a hashtable handle and generated worker functions. Names beginning with `__luash_` are reserved for generated runtime
internals.

## 8. Single-file distribution

`run_build.lua` wraps every compiler module in `package.preload`, embeds them in `dist/luash.lua`, and appends a small
dispatcher. Loading that file through `require("luash")` returns the API; executing it runs the CLI. The generated file
uses only the Lua standard library and must not read modules from the repository at runtime.

## 9. Verification architecture

Tests cover lexer/parser behavior, both serializers, complex programs, coroutine validation and state transitions,
real Bash and PowerShell execution when available, and isolated use of the bundled module and CLI. The release gate is:

```
lua run_build.lua
lua run_tests.lua
lua run_check.lua
```
